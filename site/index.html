    工作原理

    先回执，后处理；一切都写进事件流。

    每个聊天一条只追加的事件流：消息、模型输出（含思维链）、工具调用和结果全部入库，模型输入从中推导。往下滚，看一条 @ 消息是怎么走完全程的。

    gateway.events · qq:group-123
      1. 01

        Webhook 进来，立即回执

        验签（QQ 为 Ed25519）、解析，马上返回 200。平台要求很快拿到回执，剩下的事交给 waitUntil 在后台继续。

      2. 02

        去重，追加到事件流

        平台会重推，靠共享存储按消息 ID 去重。去重、写库、抢锁在同一个事务里完成，消息不会卡在交接的空隙里被漏掉。

      3. 03

        要不要唤起 agent？

        @ 和私聊必唤起；群里没 @ 的，每个窗口最多一次。锁是会话行上的租约，同一个聊天同一时刻只有一个运行者。

      4. 04

        一步一步跑 agent loop

        每一步：读事件流的新事件 → 从中推导输入、调用模型 → 输出和工具结果原样写回。回复过程中来的新消息，下一步就能看到。

      5. 05

        从原渠道回复，然后挂断

        分几条连发、回复指定消息、发表情包，说完调用 end_turn。事件流只追加，所以下一次请求是这一次的完整延续，缓存命中率常年 97% 以上。

      为 Serverless 设计

      临近 300 秒时限自动收尾或接力给新的函数实例；函数中途被杀，下一次运行从事件流补完被打断的一轮。

      像真人一样聊天

      分几条连发、回复指定消息、发表情包、主动挂断。在群里旁观没 @ 它的消息，自己判断要不要插话。

      看图、听语音

      图片缩小后入库，以前的图片也能再看；QQ 语音用平台转写。

      长期记忆

      Upstash Vector 语义检索，所有聊天共用一个记忆库，记录每条记忆的来源。

      沙盒工作区

      在 Vercel Sandbox 里跑 bash、Python、Node，每个聊天一块持久盘，文件能发回聊天。

      任意 Responses API 模型

      直接 POST /responses，默认走 OpenRouter，请求体可透传任意参数。

      三步跑起来。

      1

      部署

      点击 Deploy 按钮，或者克隆仓库后在终端里：

      $
      2

      配置

      OPENROUTER_API_KEY
QQ_APP_ID / QQ_APP_SECRET
SUPABASE_URL / SUPABASE_SECRET_KEY

      访问 /api/health 确认模型、渠道和工具都已就绪，再到平台后台填上回调地址。
